# V-K8S-REMOTE-EXEC: K8s Blocks inside a Remote Execution container

End-to-end proof that the K8s Blocks run on a remote host when a Remote
Execution container holds them, and that what comes back is the same as it
would be locally: the bound results, the objects a write leaves on the
cluster, the exec channel's three streams, the files a Copy moves, the secret
masking, the error reporting and the Block's own validation
(REQ-3.4.1.3, REQ-5.1.1, REQ-5.1.5, REQ-3.4.1.5, REQ-4.5.5,
REQ-4.5.6).

Every workflow here is generated by `cases-remote.ts` from the shared node
factories in `helpers/k8s-nodes.ts`. `fixture-remote-golden.json` is the read
workflow built from a fixed suffix and fixed namespace names, so the emitted
shape stays reviewable against a hand-readable file;
`fixture-remote-write-golden.json` does the same for the write workflow, which
is the only other node shape this suite emits.

## What this suite adds

The K8s Blocks are proved against the real cluster in `functional/k8s-read/`,
`functional/k8s-write/` and `functional/k8s-exec/`, and the Remote Execution
container is proved with HTTP Blocks in `functional/remote-exec/`. This suite
does not repeat any of them. It adds:

- every K8s read Block inside a container, on the real `sshd` host, with every
  result asserted on its BOUND VALUE after it crosses back from the remote
  worker: a map, a YAML text, an event list, a log text, a TIME and MESSAGE
  table and a usage table;
- the proof of locus. The cluster and the gateway are named by their compose
  DNS names (`kwok`, `k8s-gateway`), which resolve only inside the stack
  network. A Connect that reads the cluster version can only have run on the
  SSH host; the canvas paints the `R` badge on every body Block and on nothing
  else;
- a Secret read on the remote path, swept for both its forms on every surface
  the run is recorded on;
- a Connect through a plain-HTTP, path-prefixed gateway, whose prefix has to
  survive every request the remote worker sends;
- a Connect the plugin refuses, which must fail the same way inside the
  container as it does locally: the exact refusal, nothing connected, nothing
  after it run, the run failed;
- what the container SAYS when a host cannot carry a worker. Two hosts fail on
  purpose: one prints a notice ahead of every command's output, the other
  answers the interpreter probe and then fails to run anything. Both runs fail;
  what is asserted is that the reason the user reads is the true one;
- the same Events read on WAVE and on the host over a timestamp offset form
  only one of the two Pythons accepts, so a read that binds locally cannot
  raise remotely;
- every K8s write Block inside a container, each one read back off the cluster
  it wrote to: a ConfigMap applied from the form, a manifest whose unquoted
  date must stay text and whose trailing separator must open no second
  document, a delete and the recorded miss it leaves, a Scale and a Rollout
  Status;
- a Secret written twice on the remote path, once through the Apply form's
  declared credential and once through a manifest reading a secret variable,
  then swept for both its forms on every surface the run is recorded on;
- the exec channel inside the container: an Exec, two Scripts whose streams and
  exit codes cross back intact, and an Exec the cluster refuses, recorded and
  left amber with the run still passed;
- one file's whole round trip on one SSH session - written on the host, copied
  into the pod, read back with a `cat`, copied out to a second host path and
  read there again - plus the refusal a WAVE-side scheme earns on a Copy inside
  a Remote body.

## Prerequisites

- The real-service stack must be running (see `tests/e2e/services/README.md`).
  This suite uses six services:
  - `sshd` - the OpenSSH host (127.0.0.1:9445 -> in-stack 22) the Remote
    Execution pushes its worker to. Its `python3` meets the container's
    interpreter floor, and it resolves the other services by name.
  - `kwok` - the published kwok cluster, which the seeder reaches through its
    published port (127.0.0.1:9460) and the worker reaches as `kwok:6443`.
  - `k8s-gateway` - the nginx front of the same cluster, plain HTTP on 8080
    under the `/k8s/clusters/wave` prefix, reachable only in-stack.
  - `sshd-banner` - the same OpenSSH image (127.0.0.1:9446) whose forced
    command prints one notice line on stdout before every command's own output.
  - `sshd-badpy` - the same image (127.0.0.1:9462) whose forced command answers
    the interpreter version probe and fails everything else on stderr.
  - `k8s-stub` - the fault injector (127.0.0.1:9461, in-stack `k8s-stub:9461`),
    which serves the events and the timestamp offset form the stamp leg asks
    for.

  `tests/e2e/services/compose.yaml` declares no `depends_on`, so all six
  must be named on the up command:

  ```bash
  ./scripts/e2e-stack.sh up --wait sshd kwok k8s-gateway sshd-banner sshd-badpy k8s-stub
  ```

- The cluster's CA and its static admin token are checked-in TEST-ONLY
  material read through `helpers/config.ts`; fixture JSON never commits PEM or
  token values. Every direct Connect verifies the certificate against that CA.
  The gateway Connect carries no TLS fields at all.
- The SSH Block carries the fixture host sentinel, which the `injectSsh` import
  option rewrites for container-shard mode. The in-stack URLs are outside the
  HTTP rewrite allowlist and stay literal in every mode.

### The interpreter floor is not proved here

The container refuses a host whose `python3` is older than 3.10. The `sshd`
host sits AT the floor and the stack holds no older interpreter, so the refusal
has no host to fire against. Its unit tests own it.

### Editing anything under `tests/e2e/services/kwok/` needs a full image rebuild

The manifests, log files and tokens are copied into the image at BUILD time.
The sequence is `scripts/e2e-stack.sh build`, then `down`, then
`up --wait sshd kwok k8s-gateway`.

## Steps

1. `seedRun(request, profile)` creates the run's namespaces on the cluster and
   returns the names plus a `teardown`, one call per profile a leg reads.
2. Build the workflow from `cases-remote.ts`, import it via `POST /tests`, and
   confirm `POST /tests/{id}/validate` reports zero errors
   (`importValidateAndNavigate` with the SSH host injection on).
3. Open the test in the workbench and check the locus badges: one `R` on every
   body Block, none on the SSH Blocks, the container or the then branch.
4. Run (`startRun` / `finishRun` in `helpers/k8s-run.ts`) and read the console
   against the bookend, the Block statuses off the canvas, and the bound
   outputs in one session-variables call.
5. `test.afterAll` calls every `teardown()`.

The console is always harvested against a bookend marker on the container's
then branch, never with a bare read after a status flips. The validation leg
has no bookend to wait for, since its run fails inside the body; it waits for
the failure line itself, and the two host-diagnosis legs do the same. The stamp
leg reads the verdict before the bookend, so a run that fails inside the body
reports the reason it failed instead of timing out on a line that can never
print.

### What KR-5 asserts, and what it does not

A host that prints on stdout for EVERY exec channel poisons the worker's own
stream too, not just the interpreter probe. So this host cannot run a workflow
whatever the container does about it, and KR-5 never asserts that the run
passes. What is owed to the user is an honest reason, so that is what it
asserts: the run fails, and nothing tells the user a host with a working
`python3` has no compatible Python interpreter.

### Why KR-7 needs both sides in one workflow

The two reads are the same Block over the same events; only where they run
differs. WAVE and the pushed worker read different Pythons, and their
timestamp readers do not accept the same offset forms, so a stamp form is only
proved by binding it on both sides of one run. The `stamp` directive on the
fault injector picks the form; nothing else in the workflow changes.

### The validation rule KR-4 exercises

The Connect's timeout floor. The import and the pre-run gate both accept
`timeout: 0` (neither calls a plugin's own validation), so the refusal can only
come from the Block at run time, which is what makes it a remote-path parity
check. The other candidates (`client_cert` without `client_key`, a run token
duration under 600) are equivalent rules and were not needed.

### One leg per Playwright test, never two legs in one run

Each leg stamps its own summary marker and each spec finds that marker with
`startsWith`. The prefixes overlap: `'[KR-10] ...'.startsWith('[KR-1]')` is
true, and so is `'[KR-11] ...'`. Today that cannot bite, because every leg is
its own Playwright test with its own workbench session and its own console
buffer, so `[KR-1]` never appears in a `KR-10` or `KR-11` console. Merging two
legs into one run would break both, silently, by matching the wrong line. Do
not merge them.

### Why the manifest Secret rides a secret variable

WAVE protects a Secret value it can recognize. The Apply form's Secret Data is
a declared credential, so it is sealed in the saved test and registered with the
run before the first line is written. A hand-typed manifest is text: WAVE cannot
know a document carries a secret until it has parsed it, and by then the Block's
own input echo has already been written. So a value typed literally into a
manifest is protected on every surface the run RECORDS, but not in the saved
test and not on the Block's input echo. The route that is protected end to end
is the one `KR-9` takes: the manifest names a secret variable through a `{{ }}`
template, and the variable carries the value. The form node lists no template
field, because listing a declared credential there would unseal it at rest, and
`KR-9` asserts both halves.

### What KR-8 asserts about the Rollout verdict

kwok simulates rollout progress, so the verdict is not deterministic. The leg
pins whichever verdict the cluster reports, then asserts that the Summary's
OUTCOME cell equals the Status output and that MESSAGE is kubectl's own sentence
for that verdict - the completed sentence for `complete`, the waiting sentence
for `progressing`. Tightening it to one verdict would make the leg flake.

### Why KR-10 does not assert the exec refusal text

The reason (`InternalError`) is read structurally from the terminal Status frame
and is stable. The sentence after WAVE's own colon comes from the transport, and
the v4 and v5 transports word it differently. The remote worker runs the same
vendored client as the local Blocks, so it inherits the same limit. Only the
reason and WAVE's wrapper are asserted; adding the tail would make the leg flake.

### A Copy's paths on the remote locus name the execution host

The Copy Block's WAVE-side path resolution never runs inside a Remote Execution
container, so a plain absolute path on the WAVE side of the Block names the
execution host's own filesystem, and both Summary cells hold the paths the Block
was given, byte for byte. That is why `KR-12` exists: an `artifact://` or
`testdata://` path has no meaning there, and the run gate refuses the saved Test
rather than letting it resolve to nothing.

### What KR-11 writes, and what clears it

The two host files are removed by the leg's own last Block, `ssh-clean`, which
runs on the container's then branch. There is no SSH client in the spec's
process, so a host-side teardown can only be a Block; a run that fails inside
the body never reaches it and leaves two suffixed files behind, which disappear
when the sshd container is recreated.

The pod-side file is different. kwok's only exec target is `local`, so every
exec runs as a real process on the kwok CONTAINER's one filesystem, not inside
a pod. Deleting the namespace deletes the pods and touches none of those files:
nothing removes anything under `/wave/exec/app`, and only a kwok image rebuild
clears it. The per-run suffix is the whole isolation. `run.suffix` is minted
fresh per `seedRun` call, so the pod path this leg writes can never be the path
another run or another shard writes, and no run can read or overwrite another's
bytes. The same suffix is on both host paths, because the `sshd` container is
shared the same way. Do not add a cleanup Block for the pod-side file; it is the
one Block in this suite that cannot work.

## Seeding, teardown and isolation

- The read leg seeds four profiles at once (`get`, `events`, `logs`, `top`),
  each in its own namespaces, because one shared object set would break the
  event count and starve the metrics rows. Every Block targets the namespace
  of the profile that seeded the object it reads. If one profile fails to
  seed, the ones that succeeded are torn down before the failure surfaces.
- The write leg seeds `get`, the only fast profile that creates a Deployment
  for Scale and Rollout Status to act on. The secret-write leg seeds `minimal`:
  it writes both its Secrets itself. The exec and copy legs seed `exec`, one
  `seedRun` per spec file, so each gets its own namespace and its own suffix;
  the three pods live in `namespace` only and `namespaceB` stays empty.
- Both write legs stay inside the run namespace, so the namespace teardown is
  the whole cleanup. Neither writes a cluster-scoped object and neither writes a
  file on any host.
- The secret-read and gateway legs seed `get` only. Four legs seed nothing at
  all: the validation leg, whose Connect never reaches the cluster; the Copy
  scheme leg, which is refused before it runs; the two host-diagnosis legs,
  which never reach a cluster. The stamp leg seeds nothing either, because it
  reads the fault injector, which answers any namespace.
- The missing namespace name carries the run suffix, so no other run can make
  it exist.
- The two secret legs do not sweep the store for the SSH password: other
  suites in the same shard store it as a literal Block value on purpose, so a
  store hit would not be this run's leak. The password is swept on the console,
  the websocket feed, the session variables and the report.
- Nothing outside the run namespaces is touched. The static tokens and the
  `wave-tests` service account are read-only shared state.

## Running it

```bash
# from the root of the clone
./scripts/e2e-targeted-local.sh functional/k8s-remote-exec/<spec>.spec.ts
```

The suite runs in the `functional-workflow` project and needs its directory
glob registered in `tests/e2e/playwright.functional.config.ts`; a directory
that is not listed there never runs.
