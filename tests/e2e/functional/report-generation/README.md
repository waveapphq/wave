# V-REPORT-GENERATION-FUNCTIONAL: On-Demand Execution Report Generation

Verify on-demand report generation end-to-end: a tracked execution's report is
generated by an async job, written as an unversioned artifact, served inline, and
the rendered document's summary, timeline, errors, merged logs, level filter,
column selector, and theme switch all work. A workbench ad-hoc run generates
its session report synchronously into the session artifact dir.

## Prerequisites

- Backend running on the worker's backend port.
- Frontend running on the worker's frontend port.
- No fixtures need to be pre-seeded; the spec imports its own fixture.

## Fixtures

- `fixture.json` - One test with 6 nodes:
  - Log `Startup_Log` ("Report run started", INFO)
  - Log `Debug_Log` ("Report debug diagnostics", DEBUG)
  - Log `Warn_Log` ("Report warning threshold", WARN)
  - For `Report_Loop` (count=2) with body Log `Nested_Log`
    ("Nested iteration log", INFO) for the nested-path timeline row
  - Log `Error_Log` ("Report simulated error", ERROR) after the loop
- `fixture-warning.json` - One test with 4 nodes, for the Warning tile color:
  - Log `Open_Log` ("Warning tile run started", INFO)
  - Log `Warn_Line_Log` ("Warning tile warn line", WARN) - a WARN log LINE,
    which must not be counted as a warning Block
  - Assert `Assert_Threshold` - one literal assertion that fails with
    `fail_current_scope` off, so the Block ends `warning` and the run passes
  - Log `Close_Log` ("Warning tile run finished", INFO)

## Steps

Tracked execution:

1. Import `fixture.json` via `POST /tests`; `POST /tests/{id}/validate?context=run`.
2. On `/tests`, search the imported test and run it via the Run dialog
   (environment pick), then poll `GET /executions/{id}` to terminal.
3. `POST /executions/{id}/report`, poll `GET /executions/{id}/report` to
   completed, `POST` again.
4. Open `GET /artifacts/content/{artifact_id}?disposition=inline` and drive
   the document (level filter, columns selector, theme switch).

Workbench session:

5. Re-import, open `/workbench?editTest=<id>`, run via the canvas Run button.
6. `POST /workbench/session/report` twice; list
   `GET /workbench/session/artifacts`.
7. Open `GET /workbench/session/artifacts/content/report.html`.

Warning tile color:

8. Import `fixture-warning.json`, run it tracked via `POST /executions`,
   generate its report and open it inline.
9. Import `fixture.json`, run it tracked, generate its report and open it
   inline for the zero-warning comparison.

## Validation

- Step 1: Import succeeds; validation returns zero errors.
- Step 2: Execution reaches `passed`.
- Step 3: First POST returns 202 with a job view; polling reaches `completed`
  with full progress and `artifact_id` ending `report.html`; second POST
  returns 200 with the same `artifact_id` and exactly one
  `report.html` artifact exists (exists-check).
- Step 4: Document shows WAVE brand row, `Passed` status, test title, `Test`
  chip, full execution ID; Block Results cards 6/6 passed; timeline has one
  row per canvas node in traversal order including
  `Report_Loop / Nested_Log`; chart is expanded; one ERROR card with block
  path `Error_Log` and message; log table merges the `SYSTEM` Source and the
  Log block's Source `Log : Startup_Log` (EXEC-25);
  `Nested iteration log` appears twice; every entry carries its level; the
  level filter hides DEBUG at INFO and leaves only ERROR/FATAL at ERROR with
  the live entry count tracking visible rows; the columns selector hides the
  Time column; the theme switch toggles the `dark` class.
- Step 6: Both POSTs return 200 with path `report.html`; the session
  artifact listing holds exactly one report file.
- Step 7: The session document renders with the same structure and a
  `Session ID` meta cell.
- Step 8: The run verdict is `passed`; Block Results read Total 4, Passed 3,
  Failed 0, Warning 1; the Warning card carries `rpt-card-warn`; its number is
  amber, meaning the same computed color as the warning step row
  (`rpt-status-warning`), the warning timeline bar
  (`rpt-gantt-fill-warning`) and the WARN log rows (`rpt-row-WARN`), and a
  different color from its own gray label.
- Step 9: The Warning card carries `rpt-card-muted`, not `rpt-card-warn`;
  its number reads `0` in the same gray as its own label and a different
  color from the WARN log rows the same document still holds.
