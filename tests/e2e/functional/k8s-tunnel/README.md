# V-K8S-TUNNEL-WRITE: K8s writes through an SSH tunnel

End-to-end proof that a K8s write Block reaches a cluster WAVE can only get to
through an SSH tunnel, and that two K8s Sessions held at once in one run stay
pointed at their own clusters
(REQ-5.1.1, REQ-5.1.5, REQ-3.4.1.5, REQ-3.4.1.3).

The design the namespace lifecycle rides is K8SWRITE-1 (Apply has no Namespace
form, so a manifest is the only way to make one) and K8SWRITE-5 (Delete's
Ignore not found and Wait until gone).

The whole workflow is generated by `cases-tunnel.ts` from the shared node
factories in `helpers/k8s-nodes.ts`. `fixture-tunnel-write-golden.json` is the
same workflow built from a fixed suffix and namespace, so the emitted shape
stays reviewable against a hand-readable file.

## What this suite adds

The tunnel's reach on its own - an SSH session, a tunnel to the unpublished
cluster, and a Connect over it that reads the cluster version - is proved in
`functional/k8s-connect/`. This suite does not repeat it. It adds:

- a WRITE that lands on the far side of the tunnel and reads back with the
  value it wrote;
- a second, direct Connect to the published cluster, interleaved with the
  tunneled one, so two Sessions are alive across each other's writes;
- the split between the two clusters. They are separate apiservers, so both
  sides use the SAME namespace name and, for one pair, the SAME object name.
  The only thing that decides which cluster a Block touches is the session it
  reads.

The split legs also make the tunnel load-bearing: had session A reached the
published cluster instead, its miss leg would have hit and the shared-name read
would have carried the wrong value.

## Prerequisites

- The real-service stack must be running (see `tests/e2e/services/README.md`).
  This suite uses three services:
  - `sshd` - the forwarding-enabled OpenSSH host (127.0.0.1:9445 -> in-stack
    22) the tunnel rides. It resolves `kwok-internal` inside the stack network,
    which is what makes the forward possible at all.
  - `kwok-internal` - a kwok cluster with NO published port, container
    `wave-e2e-kwok-internal`. Nothing outside the stack network can reach it;
    the tunnel is the only route.
  - `kwok` - the published kwok cluster (127.0.0.1:9460 -> in-stack 6443), which
    session B reaches directly and which the seeder seeds through.

  `tests/e2e/services/compose.yaml` declares no `depends_on`, so bringing up one
  service does not bring up the others. All three must be named on the up
  command:

  ```bash
  ./scripts/e2e-stack.sh up --wait sshd kwok kwok-internal
  ```

  `up --wait` runs each container's own healthcheck, so a healthy
  `kwok-internal` also proves its bootstrap manifests and RBAC are in place.
- Both clusters come from the same image and carry the same static tokens
  (`tests/e2e/services/kwok/tokens.csv`) and the same PKI
  (`tests/e2e/services/kwok/pki/`), so one CA and one admin token reach both.
  All of it is checked-in TEST-ONLY material, read through `helpers/config.ts`;
  fixture JSON never commits PEM or token values.
- The tunneled Connect builds its URL from the tunnel's resolved local port and
  pins `tls_server_name` to the internal cluster's name, with certificate
  verification ON. The local port is requested as 0 and read back from the
  tunnel Block's own output - never a fixed port, because every worker's
  backend binds the same loopback.
- The direct Connect carries the literal `https://127.0.0.1:9460`, which the
  `injectHttp` import option rewrites for container-shard mode. The tunneled
  URL is outside that allowlist and stays literal in every mode.

### Editing anything under `tests/e2e/services/kwok/` needs a full image rebuild

The manifests, Stages, log files, `kwok.yaml` and `tokens.csv` are copied into
the image at BUILD time and applied from inside the container at startup.
Editing one and running `scripts/e2e-stack.sh up` leaves the old image serving
and both clusters exactly as they were. The sequence is
`scripts/e2e-stack.sh build`, then `down`, then
`up --wait sshd kwok kwok-internal`. The rebuild recreates both clusters from
scratch, so every runtime object any suite created is wiped and only the baked
bootstrap returns.

## Steps

1. `seedRun(request, 'minimal')` creates the run's namespaces on the PUBLISHED
   cluster and returns the names plus a `teardown`.
2. Build the workflow from `cases-tunnel.ts`, import it via `POST /tests`, and
   confirm `POST /tests/{id}/validate` reports zero errors
   (`importValidateAndNavigate` with both host injections on).
3. Open the test in the workbench, pick the shared environment, and Run
   (`startRun` / `finishRun` in `helpers/k8s-run.ts`).
4. Read the console between the run's bookend markers, the node execution
   statuses off the canvas, and the bound outputs in one session-variables call.
5. `test.afterAll` calls `run.teardown()`.

The console is always harvested against a bookend marker, never with a bare read
after a node status flips: the status goes terminal a beat before the console
renders its tail.

## Case ids

Every id is local to this suite. Each rides a `test.step` inside the run, except
`KT-g`, which needs no cluster and is its own test.

| Id | What it covers |
|---|---|
| `KT-a` | One run holds both sessions: the tunneled Connect and the direct Connect each read v1.33, the run stamps both versions on its marker, and every Block that is not a recording leg reports success |
| `KT-b` | An Apply through the tunnel lands and reads back with the value it wrote, under the API path the read line names |
| `KT-c` | The tunneled cluster's namespace is created and removed by the workflow itself, since nothing outside the run can reach it |
| `KT-d` | The same ConfigMap name in the same namespace carries a different value on each cluster, chosen only by the session the Block reads |
| `KT-e` | An object written through one session is not there through the other: the cluster's own NotFound wording, exactly one WARN line each, both Blocks amber, and the run still passed |
| `KT-f` | The tunnel carries the whole write sequence and the workflow closes it while it is still open, so the session close never had to reap it |
| `KT-g` | The node factories emit the checked-in workflow shape |

## The run, block by block

| Block | Session | What it does |
|---|---|---|
| `open-session` | - | Opens the SSH session the tunnel rides |
| `tunnel-open` | - | Forwards an auto-assigned local port to the unpublished cluster |
| `connect-a` | A | Connects over the tunnel, SNI and CA verification on |
| `connect-b` | B | Connects to the published cluster directly |
| `ns-a` | A | Applies the run namespace as a manifest |
| `apply-a-solo` | A | Writes the ConfigMap only the tunneled cluster holds |
| `apply-b-solo` | B | Writes the ConfigMap only the published cluster holds |
| `apply-a-both` | A | Writes the shared-name ConfigMap with the tunneled value |
| `apply-b-both` | B | Writes the shared-name ConfigMap with the published value |
| `get-a-solo` | A | Reads the tunneled ConfigMap back - the roundtrip |
| `get-b-both` | B | Reads the shared name and gets the published value |
| `get-a-both` | A | Reads the shared name and gets the tunneled value |
| `get-b-miss` | B | The tunneled ConfigMap is NotFound here (Record and continue) |
| `get-a-miss` | A | The published ConfigMap is NotFound here (Record and continue) |
| `log-roundtrip` | - | The run's one marker line, carrying both versions and every count |
| `delete-a-ns` | A | Removes the run namespace from the tunneled cluster |
| `tunnel-close` | - | Closes the tunnel while it is still open |
| `close-session` | - | Closes the SSH session |
| `log-done` | - | Bookend |

The delete comes before the tunnel close, because after the tunnel closes there
is no route left to that cluster. The tunnel close comes before the session
close, because a session close cascades and reaps any tunnel still open, and a
tunnel closed that way reports `closed=false`.

## Seeding, teardown and isolation

- The PUBLISHED side is seeded and torn down the usual way: `seedRun` creates
  `wave-e2e-<suffix>` and `wave-e2e-<suffix>-b`, and `test.afterAll` deletes
  them. Every object this suite writes there lives in `wave-e2e-<suffix>`.
- The TUNNELED side has no seeding path. `helpers/k8s-seed.ts` builds its URL
  from the published cluster's host and port, and the tunnel listener lives on
  the WAVE backend's own loopback, which in container-shard mode is inside the
  shard container. So the run creates its namespace on that cluster with an
  Apply Block and removes it with a Delete Block, both inside the workflow.
- The namespace name is the SAME on both clusters. Two apiservers means the name
  is free on each, and reusing it is what makes the split legs conclusive: the
  namespace, the kind and (for one pair) the object name are identical, so the
  session is the only variable left.
- Every object name carries the run suffix, so a run that dies before its Delete
  leaves nothing a later run can collide with. Such a leak survives on the
  tunneled cluster until the image is rebuilt; there is no route from the test
  process to clean it.
- The Delete of the namespace does not wait for it to be gone. The namespace
  goes to Terminating and drains after the run, and the Block's wait is bounded
  by its own request timeout.
- Nothing else on either cluster is touched. The static tokens are read-only
  shared state, the baked `restricted` namespace is never written, and no
  cluster-scoped object outside the run's own namespace is created or removed.

## Running it

```bash
# from the root of the clone
./scripts/e2e-targeted-local.sh functional/k8s-tunnel/v-k8s-tunnel-write.spec.ts
```

The suite runs in the `functional-workflow` project and needs its directory
glob registered in `tests/e2e/playwright.functional.config.ts`; a directory that
is not listed there never runs.
